## cr-ls1-9 — production checker concurrency has no effective guard

> Replacing `Some(&local.checker_pool)` with `None` at
> `mod.rs:4983` left the test green. Its converged phase has identical
> sequential and parallel outcomes; its changed phase lets the default run
> repair both files, then expects the 1- and 16-checker runs to copy zero.
> The pool unit test did go red when the pool itself was forced to one
> worker, but it cannot detect production wiring removal, so the load-bearing
> feature can disappear while all added tests pass.

**This is the SEVENTH vacuous guard in this slice, and the second of the
exact same kind.** cr-ls1-8 was "the parallel-diff test does not guard
parallelism". The replacement I wrote for it guarded the pool in isolation
and the option's plumbing, and still left the one edge that matters — *does
the production diff use the pool* — untested. The reviewer also caught a
second defect inside the same test that I had not: its changed phase let the
first run converge the tree, so the later settings asserted zero copies
against nothing to copy.

### Fix

`CheckerPool` counts `install()` calls, and `LocalMirrorOptions` gained
`checker_pool: Option<CheckerPool>` so a test can hold the very pool the
session will use — the same injection seam `phase_probe` already uses, for
the same reason. The test now asserts `pool.installs() > 0` after a real
session.

The per-setting loop was also repaired: each iteration re-diverges the tree
with a body of a DIFFERENT LENGTH, because equal-length rewrites inside one
mtime tick compare as unchanged under size+mtime — which is how the previous
version ended up asserting against a converged tree.

**Guard proof**: the reviewer's exact edit — `Some(&local.checker_pool)` →
`None` — now reds on
`the destination diff never dispatched onto the checker pool`. Restored and
green.

## cr-ls1-10 — the diagnostic pin is silently ignored on remote routes

> `TransferArgs` exposes the hidden `--checkers` flag for every copy, mirror
> and move route, but only the local route consumes it. Every wire-carrier
> diff explicitly passes no checker pool, and the remote support gates do not
> reject a nonzero value. A diagnostic remote invocation accepts
> `--checkers N` while running unchanged, which can invalidate performance
> measurements.

Correct, and it defeats the flag's only purpose. `--checkers` exists solely
to make a measurement trustworthy (D-2026-08-01-1 removed every other reason
for it to exist); a pin that quietly does nothing produces a number the
operator believes and shouldn't.

### Fix

`reject_unsupported_checker_pin` refuses a non-zero pin on any non-local
route, wired once per dispatch — `if !matches!(route, LocalToLocal { .. })`
— rather than per-arm, so a route added later cannot silently swallow it.
`0` (discover at runtime) stays valid everywhere.

**Guard**: `a_checker_pin_is_refused_where_it_cannot_take_effect` asserts
both the refusal and that the message names the flag and the remedy.

## Standing note
