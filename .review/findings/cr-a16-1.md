## The finding, as returned

> Remote push with explicit `-p` but without `-v` loses the
> source-enumeration heartbeat introduced as a preserved fallback. The
> CLI creates a progress handle for `-p`, but run_remote_push constructs
> FsTransferSource with only execution.verbose and never attaches that
> handle to the source, so the source is both sinkless and non-verbose
> and the new gate suppresses its raw heartbeat. This contradicts the
> range's `(or -p)` documentation and can leave a slow remote enumeration
> silent until destination-side progress begins.

## Why it is admitted

Correct: the audit-16 fix preserved `verbose || progress` on the LOCAL
route (`run_local_session`) but threaded only `execution.verbose` on the
remote-push route, so the documented "(or `-p`)" liveness fallback holds
on one route and not the other. The full fix (attaching a real progress
sink to the remote source — CLI_LIVE_PROGRESS residue (d)) stays
post-1.0; the minimal parity fix restores the documented contract.

## Fix (prescribed)

Mirror the local shape: the remote-push route passes
`verbose || progress` into `FsTransferSource::with_verbose`, so plain
`-p` keeps the raw heartbeat exactly as it did before the audit-16 gate.
Guard at the seam the reviewer used: a remote-push invocation with `-p`
and without `-v` must still emit the enumeration heartbeat.

## Fix (as built)

Exactly as prescribed, plus the one thing the prescription left open —
WHERE the remote route learns about `-p`.

- `PushExecution` gains `progress: bool` beside `verbose`;
  `run_remote_push` passes `execution.verbose || execution.progress` into
  `FsTransferSource::with_verbose`, the same shape `run_local_session`
  already uses.
- The CLI (`crates/blit-cli/src/transfers/remote.rs`) fills it from
  `args.effective_progress()` — the identical effective decision
  `LocalMirrorOptions.progress` carries, so `-p` means the same thing on
  both routes.
- **A new field rather than `progress.is_some()`** on the handle already
  in `run_remote_push`'s signature. That handle is the SESSION's progress
  lane, and the TUI passes `Some(&progress)` on every F1 push while
  wanting silence: deriving from it would have started painting raw
  "Enumerated N entries…" lines onto the TUI's own surface, trading this
  bug for a worse one. `build_f1_push_execution` sets `progress: false`
  explicitly, with the reason recorded at the field.
- Untouched, as scoped: attaching a real progress sink to the remote
  source (CLI_LIVE_PROGRESS residue (d)) stays post-1.0.

**Guard proof** (byte-identical SHA-256 restore:
`crates/blit-app/src/transfers/remote.rs` DF877935…60BB):

- Seam: `remote_push_with_progress_keeps_the_enumeration_liveness`
  (`crates/blit-cli/tests/live_progress_row.rs`) drives the REAL binary
  with `-p` and no `-v` against a real daemon, which is where the CLI's
  `-p` decision, `PushExecution.progress` and the source construction
  actually meet — a unit test on the expression would pin the fix rather
  than the behaviour. It asserts the push LANDS before asserting on
  stderr, so the liveness assertion cannot pass over a transfer that
  never happened.
- Reverting `|| execution.progress` to bare `execution.verbose` reds
  exactly that test, printing the whole silent stderr (`starting copy …
  -> 127.0.0.1:PORT:/test/`, and nothing else). The three local-route
  tests in the same binary stay green — they cannot see that route at
  all, which is why the finding survived audit-16 in the first place.
- That binary now owns audit-16's gate end-to-end on BOTH routes: quiet
  by default, audible under `--verbose`, audible under `-p`.
