## cr-ls1-14 (MEDIUM) — the unit test made an uncontrolled network connection

> The `checkers=0` assertion proves the value is accepted by continuing
> through the real remote-pull path against `host:/src/` and expecting
> connection failure. This performs DNS and network I/O, took 1.29 s here,
> and **can behave differently or write under `/dst` if that hostname
> resolves to a Blit daemon.**

Taking this one first because it is the one that could have done damage. I
wrote a unit test that resolves an attacker-or-accident-controlled hostname
and, on a machine where `host` resolves to a live blit daemon, would have
initiated a real transfer writing into `/dst`. It ran on every
`cargo test --workspace`. That is not a flaky test, it is a test that can
perform I/O nobody asked for, and I added it while fixing a finding about
tests that do not test what they claim.

### Fix

The negative case is asserted against the helper with a route built by
`select_transfer_route`, which is deterministic and touches nothing. The test
first asserts the fixture really is a remote route, so it cannot quietly
degrade into checking the local case. The end-to-end positive case moved to
`tests/checker_pin_gate.rs` against LOCAL paths.

## cr-ls1-13 (LOW) — the ordering claim had no guard

> The test claims unsupported pins are refused before banners or destructive
> prompts, but it only checks the returned error and sets `yes=true`. I moved
> both validations back after their prompts and startup banners; the intended
> test remained green and emitted all three banners.

**Ninth vacuous guard.** Same shape as the last three: I asserted the
outcome (an error is returned) and not the property I had actually claimed
(it is returned *before* anything reaches the operator). Ordering is not
observable from inside the process, so it was never going to be provable
where I put it.

### Fix

New integration test `tests/checker_pin_gate.rs` drives the real binary and
asserts on its real output: the refusal names the flag, and the output
contains **no** startup banner, **no** `Continue?` prompt and **no**
"will delete" description, for `copy`, `mirror` and `move`.

Two deliberate choices:
- **`--yes` is NOT passed.** If the gate ever moves back below the
  confirmation, mirror and move block on stdin and the timeout fails the
  test. It cannot silently pass either way.
- The endpoint is `blit.invalid:`, reserved by RFC 6761 and guaranteed
  never to resolve, so even a total failure of the gate cannot contact a
  real host — the mistake cr-ls1-14 is about.

**Guard proof**: moving both gates back to immediately before `match route`
(the reviewer's mutation) reds it with
`copy printed its startup banner before refusing`. Restored from HEAD and
green.

## Standing note, updated

Nine vacuous guards. The three-strikes pattern from `cr-ls1-11-12.md` now has
a fourth instance, and a sharper statement of the rule:

**Assert the PROPERTY CLAIMED, not a consequence of it.** "Refused" and
"refused before any output" are different claims and need different
assertions; the first cannot imply the second. Every repeat in this slice has
been an assertion on a consequence — a file set, an error value, a return
code — where the claim was about a mechanism.
