## Evidence
crates/blit-core/src/transfers/filter.rs:446 — escaped literal components reach ExcludeRules, whose fs_enum.rs:131 fallback also compares the encoded pattern as ordinary text. Reproduced with alias pointing to src/data[1], alongside src/data[[]1[]] and src/data1. Copying with --exclude <alias> omitted both data[1]/private.txt and the unrelated data[[]1[]]/private.txt, while copying data1/private.txt. The generated ./data[[]1[]] matches the intended name through globset and the unrelated encoded name through glob_match.

## Predicted observable failure
Copy or backup silently omits an unrelated subtree whose name equals an escaped pattern's textual representation, despite successful completion.

## Reviewer's suggested approach
Evaluate escaped patterns consistently as globs; do not additionally interpret their encoded text through the exact/prefix fallback. Add a negative control containing the escaped representation as an actual filename.

## Intake
Admitted; reproduced by the orchestrator with the release binary on macOS: `alias2 -> s2/data[1]`, siblings `s2/data[[]1[]]` and `s2/data1`, `blit copy s2/ d2/ --exclude <alias2>` copied only `data1/private.txt` — `data[[]1[]]/private.txt`, never named, was left out. cr-g3fix2-2's Known gaps called this pre-existing behaviour of the fallback; it is not: before the escaping no rule text ever equalled an encoded name, so the fallback could not misfire this way. Root cause: `ExcludeRules::excludes` (`fs_enum.rs:118-135`) evaluates every rule twice — through the compiled globset and through `glob_match` (`fs_enum.rs:532`, a legacy matcher: exact text compare, or `*`-prefix/suffix/contains) over the raw pattern text — so the escaped text `data[[]1[]]` equals a real name of that spelling. Fix shape: a pattern the globset compiled is evaluated as a glob only; the text fallback runs, if at all, only for a pattern the globset refused (establish what `glob_match` still supplies — read `FileFilter::build_globset` and the callers; if nothing, drop the fallback from `ExcludeRules` and say so). Guards: the alias-into-`data[1]` guard gains the sibling `data[[]1[]]` as a negative control (kept) in the unit test and the CLI test; a direct `ExcludeRules` test that an escaped literal rule matches its real name and not its encoded spelling; the existing rules (name at any depth, anchored, subtree, trailing `/`, `*.log`, `**/*.log`, `dir/**`) stay green; all mutation-red.

## What
An escaped literal now matches only the name it was written for. With `alias -> src/data[1]` and the siblings `data[[]1[]]/` and `data1/`, `--exclude <alias>` (written `./data[[]1[]]`) leaves out `data[1]/` alone; the sibling actually spelled `data[[]1[]]` is copied, as is `data1/`. Before, every exclude rule was evaluated twice — as a glob and as plain text — and the text arm compared the escape's own spelling with the entry's name, so a directory spelled like the escape was left out too, with no warning.

## Approach
- What `glob_match` (`fs_enum.rs`, the legacy text matcher: `*`, `*x*`, `*x`, `x*`, or an exact compare) supplies, established by reading its callers — `ExcludeRules::excludes` (names and paths), `FileFilter::excluded` (the whole pattern against the bare name and the relative path), the `--include` test in `allows_entry`, and `exclude_dirs` in `should_include_dir` — and `FileFilter::build_globset`: for a pattern `globset` compiles, every match the text arm makes is also a match of the compiled glob (globset is built with its defaults, so `*` crosses `/` just as the text compare does, and case is compared the same way), except where the pattern holds glob syntax (`?`, `[`, `{`, `\`), which the text arm reads as literal characters. The escaped literals cr-g3fix2-2 writes are exactly such patterns, so for a compiled pattern the arm adds nothing but this misreading. It still supplies something for a pattern `globset` refuses (for example an unclosed class `*[x`, which as text is a suffix compare). Validation rejects every such pattern on the CLI and wire paths (`build`/`build_spec` through `validate_globs`, a daemon's `filter_from_spec`), so only a `FileFilter` built directly (an embedder) can still carry one. `build_globset` itself silently drops refused patterns.
- `CompiledPatterns` (new, `fs_enum.rs`): the `GlobSet` of the patterns `globset` accepts, plus the patterns it refused. All of them count as refused when the set as a whole cannot be built, which matches today's behaviour of an empty set with every pattern compared as text. `is_match` is the glob set, or `glob_match` over the refused patterns only. So a compiled pattern is evaluated as a glob only, and the text comparison runs only for a pattern the globset refused (the fix shape's "if at all": kept for refused patterns so a filter built directly behaves as before; dropped for everything else).
- `ExcludeRules` holds a `CompiledPatterns` for its names and one for its paths, in place of the pattern lists and glob sets it evaluated side by side. `FileFilter::excluded` (the whole-pattern arm) uses a cached `CompiledPatterns` over `exclude_files` (`compiled_files`) instead of a glob set plus `glob_match` over every pattern. The text arm in `excluded` misread an escape the same way (`data[[]1[]]/notes` equalled the path of an entry spelled `data[[]1[]]/notes`, and `prefix*` forms compared prefixes), so it falls under the same rule. The two arms are guarded separately.
- `--include` and `exclude_dirs` keep their text arm: no escaped literal reaches them (`--include` is passed as typed, and `exclude_dirs` has no CLI flag). See Known gaps.
- A consequence within scope: a typed relative `--exclude` holding glob syntax is now that glob only. `--exclude 'data[1]'` is the class (it names `data1`) and no longer also leaves out an entry literally named `data[1]`. Typed components were already defined as glob syntax (cr-g3fix2-2); a literal name holding glob syntax is excluded by its absolute path (escaped when it is resolved) or by writing the escape.
- Cost (FAST): unchanged or lower. Each test is one `GlobSet` match per component prefix; the per-pattern text compare per component is gone for compiled patterns.
- No deviation from the admitted fix shape. The fallback was not dropped from `ExcludeRules` outright, because it still supplies a match for a refused pattern; it now runs for those alone.

## Known gaps
- `--include` and `exclude_dirs` keep the text arm for every pattern: a typed `--include 'a[1]'` still also matches a file literally named `a[1]`. No escaped literal reaches either, so this finding's misreading cannot occur there; making them glob-only would change typed `--include` behaviour outside this finding.
- A refused pattern is still compared as text. Only a filter built directly can hold one: every CLI and wire path rejects it first.
- If a whole `GlobSet` cannot be built (a regex past globset's size limits), every pattern of that set is compared as text, as before the fix, so the misreading could return in that degenerate case.
- K2 and K3 need symlinks and are Unix-only; K1 runs on every OS (Windows by CI). Verified on macOS aarch64 only, plus the Linux and Windows cross-clippy at the final gate; Linux and Windows runtime tests were not run here.
