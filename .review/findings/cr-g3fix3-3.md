## Evidence
crates/blit-core/src/transfers/filter.rs:466 — a resolved Unix name back\slash is emitted as ./back[\]slash. On Windows, fs_enum.rs:83 invokes normalize_separators, whose line 147 rewrites this to ./back[/]slash. A temporary test against the actual ExcludeRules::compile branches confirmed that the Unix rule leaves back/slash/saved.txt in scope while the Windows rule excludes it. The remote mirror consumes these rules through transfer_session/mod.rs:4181. This was verified through the parameterized compiler on macOS, not a Windows runtime.

## Predicted observable failure
A Unix-to-Windows mirror excluding an aliased directory containing a literal backslash also excludes the unrelated destination subtree back/slash from deletion, retaining stale files outside the requested exclusion.

## Reviewer's suggested approach
Preserve a canonical wire-pattern dialect and normalize native separators before escaping, without rewriting escaped literals on the receiving peer. Test Unix-generated wire patterns under both platform rules.

## Intake
Admitted on the reviewer's analysis (the parameterized `ExcludeRules::compile` under the Windows rule, run on macOS; no Windows runtime), the same footing as cr-g3fix-3. cr-g3fix2-2's Known gaps noted the rewrite and dismissed it because no Windows name can hold `\`; the consequence it missed is that the rewritten class `[/]` then matches a real separator, so `back/slash` — an unrelated destination subtree — leaves the mirror's deletion scope. Root cause: cr-g3fix-3 put the typed-input rule "on Windows `\` is a separator" into `ExcludeRules::compile` (`fs_enum.rs:83`), which is also where every wire pattern a daemon receives (`filter_from_spec`, consumed at `transfer_session/mod.rs:4181`) is compiled, so a canonical wire pattern is re-read as typed input. Fix shape (the reviewer's): the wire dialect is canonical — `/`-separated, literals escaped — and the receiving peer never rewrites it; native separators are normalized once, where typed input enters, before escaping. Mechanism is the agent's call between (a) moving the normalization out of `compile` to the typed entry points (`resolve_excludes_on` already does it; find every other path a typed pattern takes into a `FileFilter` on Windows, so a Windows user's `.\cache` still anchors through the CLI, and redefine cr-g3fix-3's embedder guard `backslash_forms_match_on_windows` only with the embedder contract stated in the `FileFilter`/`ExcludeRules` doc comments and the finding doc) and (b) keeping `compile`'s normalization but leaving a bracket class untouched (`[\]` produced by `literal_glob`; the class syntax `globset::escape` emits is `[x]` per character) — (a) is cleaner and is the recommendation, (b) is the smaller change; either way record the reasoning. Guards: a Unix-generated wire pattern `./back[\]slash` compiled under the Windows rule must leave `back/slash/saved.txt` in scope and must still not match it under the Unix rule; a Windows-typed `.\cache` through `resolve_excludes_on` under the Windows rule still anchors; cr-g3fix-3's existing guards stay green (or are redefined with the reasoning); all mutation-red; the `cfg(windows)` runtime proof is CI's Windows leg.

## What
A Windows peer no longer turns a Unix peer's escaped backslash into a separator. A Unix client excluding an aliased directory named `back\slash` sends `./back[\]slash`. A Windows daemon now compiles that as a pattern that names no Windows path, so the unrelated destination subtree `back/slash/` stays in the mirror's deletion scope. Before, `ExcludeRules::compile` rewrote the pattern to `./back[/]slash`, whose class matches a real separator, and `back/slash/` was kept out of the deletion pass. A Windows user's typed `.\cache` still anchors.

## Approach
- Mechanism: (b), keeping the separator rule in `compile` but leaving a bracket class untouched, rather than the recommended (a), moving the rule out of `compile`. The deciding fact comes from globset 0.4.20's own Windows reading (`glob.rs` `parse_backslash`, 887-898; `parse_class`, 962-1051). On Windows `backslash_escape` defaults to off and `\` is a separator, so globset itself compiles every bare `\` in a pattern as `/` (`Token::Literal('/')`), while a `\` inside a class is an ordinary member on every platform. As a result:
  - Under (a) the receiving peer would still rewrite a bare `\`, because its glob compiler does. The property "the receiving peer never rewrites" cannot be had for a bare `\` without overriding globset's platform default. Meanwhile the text the rules are classified from (the `./` anchor, the trailing-`/` trim, name versus path) would disagree with the glob on Windows. For example, an embedder's `.\cache` would be classified as a name while globset compiles `./cache`, so it would match nothing. And cr-g3fix-3's embedder contract would shrink for no gain on this finding.
  - Under (b), `compile` reads a pattern exactly as the Windows glob compiler does: a bare `\` is a separator, a class's `\` is literal. The anchor and name/path classification therefore agree with the glob. A canonical wire pattern (`/`-separated, with literals escaped as `[x]` classes by `globset::escape` / `literal_glob`) passes through unchanged on every peer, because its only `\` is inside a class. cr-g3fix-3's guards and its embedder contract stay as they are.
- `normalize_separators` (`fs_enum.rs`) under the Windows rule now copies a bracket class verbatim and writes `/` only for a bare `\`. `bracket_class_len` (new) finds a class's extent the way globset's `parse_class` does: `[`, an optional `!` or `^`, then a `]` in first place is a member, and the class ends at the next `]`. An unclosed `[` is an ordinary character (globset refuses that pattern). Under the Unix rule the pattern is still returned as typed, borrowed.
- The function has two callers, so one change covers both. `ExcludeRules::compile` covers the receive path (`filter_from_spec` → `FileFilter::subtree_rules`, consumed by the mirror deletion scope at `transfer_session/mod.rs:4181`). `resolve_excludes_on` covers typed input, where native separators are normalized once, before a resolved name is escaped. A Windows user who types a class holding `\` (`data[\]x\y`) now keeps the class (`data[\]x/y`), as globset reads it there. Before, it became `data[/]x/y`, which matched a separator: the same misreading at the typed entry.
- Doc comments updated: `ExcludeRules` (a class is never rewritten, see `normalize_separators`), `normalize_separators`, `ResolvedExcludes::patterns`, `resolve_excludes`.
- Deviation from the recommendation, recorded per the intake: (b) instead of (a), for the reason above. The admitted contract holds. The wire dialect is canonical; the receiving peer never rewrites a canonical pattern (its escapes are classes, which are copied); native separators are normalized where typed input enters, before escaping. `backslash_forms_match_on_windows` is not redefined, because the embedder contract is unchanged.

## Known gaps
- A bare `\` from a Unix peer is still read as a separator by a Windows peer: a Unix user's typed relative escape (`--exclude 'a\*b'`, meaning the literal name `a*b`) becomes `a/*b` there. This happens with or without `compile`'s rewrite, because globset on Windows compiles a bare `\` as `/`. Closing it would mean writing a typed Unix escape `\x` as the class `[x]` before the pattern leaves a Unix client, or compiling received patterns with `backslash_escape` on everywhere. Both are wider changes to the typed and wire dialect than this finding; not done. The escape our code generates (`[\]`) is a class and is unaffected.
- The class scanner mirrors globset 0.4.20's class syntax. A future globset that changes class parsing (for example, escape processing inside a class) would need the scanner to follow.
- W1's literal-name assertion (`back\slash/saved.txt` is excluded) runs off Windows only: on Windows `Path` splits that string at `\`. W1's wire-path part runs under the host's rule, so on macOS it cannot go red for the Windows-only regression (R2 is caught by W1's parameterized part instead); on CI's Windows leg it can.
- Verified on macOS aarch64 only, plus the Linux and Windows cross-clippy at the final gate; Windows runtime tests were not run here.
