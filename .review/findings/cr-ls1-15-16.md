## cr-ls1-15 — the adaptive-default test bypassed the route it claimed to guard

> The adaptive-default test uses two local paths, but local routes are
> EXEMPT from the checker-pin gate; the only remote `checkers=0` assertion
> calls the helper directly. I added a dispatch-only rejection of
> `checkers=0` on non-local copy/mirror routes, and both added integration
> tests plus the modified unit test stayed green. A default remote transfer
> would therefore be rejected without these targeted guards noticing.

**Tenth vacuous guard.** The claim was "the adaptive default is not refused
on a remote route"; the fixture used a local route, which the gate never even
inspects. Asserting a property on the one input shape that cannot exhibit it.

## cr-ls1-16 — the fixture could still resolve and write outside test storage

> The regression fixture assumes `blit.invalid` can never resolve and uses
> the fixed destination `/tmp/blit-gate-dst`. RFC 6761 controls DNS
> treatment, but system resolution can still honor a local hosts-file
> mapping. If the gate is removed, the copy case can consequently contact a
> live default-port daemon and populate that non-temporary destination — the
> same side-effect class this change is meant to eliminate.

Correct, and it is the cr-ls1-14 hazard surviving its own fix. I replaced a
network-reaching fixture with one that merely *probably* cannot reach the
network, and wrote to a fixed path outside test-owned storage while doing it.

## Fix (one fixture change closes both)

Every case now uses a **missing local source paired with a remote
destination**, which the reviewer proposed and which does three jobs at once:

1. It selects a genuinely remote route (`LocalToRemote`), so the gate is
   actually exercised — closing cr-ls1-15.
2. It cannot reach the network under ANY behaviour of the gate: the
   source-existence check lives in the dispatch arm, BELOW the gate, so a
   removed or inverted gate fails on the missing source instead of
   connecting — closing cr-ls1-16 structurally rather than by assumption
   about DNS.
3. It gives the adaptive case an unambiguous post-gate signal: reaching
   `source path does not exist` proves the run got past the gate on a remote
   route, which is exactly the claim.

The source path lives in a `tempfile::TempDir` that is removed on drop, so
nothing is written outside test-owned storage even in the failure modes.

The pin case additionally asserts it does NOT reach
`source path does not exist`, which pins the gate ahead of the dispatch from
the other direction.

**Guard proof**: the reviewer's exact mutation — dropping `args.checkers != 0`
so the gate rejects every remote route — reds
`the_adaptive_default_reaches_the_remote_dispatch` with "the adaptive default
must never be refused by the pin gate". Restored byte-identical
(`BFF68738…6C1A`), green after.

## Standing note

Ten vacuous guards. cr-ls1-15 adds a third distinct sub-species to the list
already in `cr-ls1-13-14.md`:

1. Asserting a CONSEQUENCE instead of the claimed property (file sets, error
   values, return codes).
2. Testing the IMPLEMENTATION instead of the seam where it is used.
3. **Choosing an input shape that cannot exhibit the property** — a local
   route to test a gate that only fires on remote ones.

All three are answered by the same discipline, which has caught every one
when actually applied: run the revert, and check the test goes red for the
stated reason.
