# Exclude case matching: `--match-case` default, `--ignore-case`, and the one-line prompt

**Status**: Active — owner: "yes" (2026-11-20, D-2026-11-20-1), after the interview begun 2026-10-21 and resumed 2026-11-20 settled Q1 to Q11; Design §Matching revised the same day (D-2026-11-20-4): `--ignore-case` widens the pattern and leaves names untouched
**Created**: 2026-10-21
**Supersedes**: `docs/plan/MIRROR_GLOB_DEST_ONLY.md` (Draft r3, same day — its mechanism options are all withdrawn; its prior-art measurements of robocopy and rsync stand and are referenced below); the first bullet of `docs/RELEASE_NOTES_1_0.md` "Known limitations shipped open", once this ships
**Decision ref**: D-2026-11-20-1

## Goal

A user who gives a pattern to a command that can delete is told, in one line and in their own words, how that pattern will match on this run, and chooses. Patterns match exactly as typed by default (`--match-case`, the rsync rule, the same on every machine). `--ignore-case` makes every pattern in the command ignore capital letters, on the source walk and in the destination's deletion scope alike, on every machine. When a delete option is in effect, `-y` is absent, and the user has NOT chosen a mode (neither `--match-case` nor `--ignore-case` typed, Q9), the existing confirmation prompt gains one line that echoes the user's actual pattern and the spellings it will and will not match; with either option typed the user has already chosen, so only the normal delete warning prints. `-y` bypasses the prompt as today. `copy`, which has no prompt and gains none, prints the same line as a note and goes on (Q3). Nothing depends on which filesystem the destination has.

## Owner requirements (2026-10-21, verbatim where quoted)

- "FAST, SIMPLE, RELIABLE" — the earlier proposals (disk-detected case mode; regex-style `(?i)` prefix; Unicode-table pairing; filesystem-lookup pairing) were rejected as violating two of the three.
- "it cannot be internally inconsistent" — one reading of a pattern per run, the same for what is copied and what is deleted.
- "I would expect ß to mean that exact character, not transliterated to ss" — no fold or transliteration changes which letters a pattern names. Ignoring case maps one letter to the same letter in another case, never to a different letter or a different number of letters.
- "same as the decades old established tools, unless you have a compelling, real-world reason to subvert people's expectations" — rsync matches exactly; robocopy matches with Windows' own case-insensitive rule; both protect excluded destination-only entries from deletion and both delete a destination-only entry no exclude names (measured and read from source in `MIRROR_GLOB_DEST_ONLY.md` §Prior art).
- "it's a flag users will only look for after they've lost data" — hence the prompt line: the choice is presented at runtime, before the delete, not discovered afterwards.
- "when data loss is possible, this cannot be ambiguous even to novices" — the prompt line says what blit will do, in the user's own pattern, not what a filesystem might do.
- "we have a prompt whenever a delete option is specified without -y, so if -y is not included and a CLI option with a pattern is included, there should be a short, 1 line blurb about the matching issue … with -y bypassing it. --match-case is the default, and --ignore-case does extra work on case sensitive filesystems."
- "that requires us to know what the remote target's filesystem is, so that's a daemon change" — the line therefore states blit's own rule, which is identical everywhere, and needs no probe of the destination's disk.
- "the example needs to be the actual string the user entered."
- "if the user specifies --ignore-case and not -y then the message should not print, just the normal delete warning" — the line exists to present a choice not yet made; once made, it is silent.
- "if we have an include from, we need an exclude from. so --files-from needs an exclusion analog. every entry in either needs to be exact or a [pattern], so users with a 50 line file won't miss something and delete all their .Jpg files" — hence `--exclude-from FILE` and `--include-from FILE` (one pattern per line, blank lines and `#` comments ignored; the line rule is the one `--files-from` already follows, Q5 — not rsync's, which keeps edge whitespace), each line treated exactly as one more command-line pattern under the run's one case mode; `--files-from` stays the literal name list it is today. (Owner wrote "regex"; blit's patterns are globs — `*.jpg` — and a file line is an exact name or a glob, the same syntax as the option. Reading confirmed by the owner 2026-11-20, Q7 "a": globs here, regular expressions in a plan of their own.)

- 2026-11-20, on the measurements recorded below and in Open questions: `--ignore-case` covers patterns only, never the `--files-from` list (Q2 "a"); a pattern file is read by the rule `--files-from` already follows, both ends stripped (Q5 "a", after "these are extremely consequential decisions that I cannot simply answer in a vacuum" and the measurements that followed); a saved job keeps the patterns read, not the file's path (Q6 "a"); `copy` prints the matching line as a note with no question (Q3 "b", after `copy` was measured overwriting a destination file an exclude missed by case); a typed `--match-case` silences the line exactly as `--ignore-case` does (Q9 "a"); the three 2026-10-19 cases are expected behavior, not a defect (Q4 "a", after rsync was run deleting the same entries); `?` and classes keep counting bytes, and a class holding a non-ASCII character is refused (Q10 "b"); patterns here are globs, and regular expressions — "why can't we support regex in both?" — get a plan of their own (Q7 "a"); a pattern-file line written as an rsync rule (`- `, `+ `, `!`) refuses the run (Q8 "a").
- 2026-11-20, on the other verbs that take patterns: "find should work identically to the unix find command. I don't know what check is." — `find` therefore leaves this plan for one of its own (Q11); `check`, once explained, takes the transfer verbs' pattern options (Q11 "a").

## Prior art: how established tools read a pattern file (owner question 2026-11-20: "do you need to see the rsync source? how does robocopy do it?")

Measured 2026-11-20 on the Linux host `continuum` with rsync 3.5.2 (build `41bbd895`), git 2.56.1 and GNU tar 1.35, and on the Windows host NETWATCH-01 (Windows 10.0.26100.33822) with robocopy 10.0.26100.1. Each case wrote a one-pattern file byte-exact and offered a name with and without the whitespace in question: for rsync a real `rsync -a --delete --exclude-from` run over a destination-only entry, for robocopy a real `/MIR` run from a job file, for git `check-ignore` against an ignore file, for tar an archive made with its exclude-file option.

| Line in the file | rsync | robocopy job file | git | GNU tar | blit `--files-from` today (code read, not run) |
|---|---|---|---|---|---|
| trailing space | kept, part of the pattern | stripped | stripped | stripped | stripped |
| trailing tab | kept | stripped | kept | stripped | stripped |
| leading space | kept | stripped | kept | kept | stripped |
| Windows line ending (CR LF) | CR stripped | its own format; LF-only also read | CR stripped | CR stripped | CR stripped |
| line starting `#` | comment | a pattern | comment | a pattern | comment |
| line starting `;` | comment | a pattern | a pattern | a pattern | a name |
| spaces-only line | a pattern (it kept a file named three spaces) | not measured | blank | blank | blank |

- **The rsync result that matters:** a file holding `*.jpg` followed by one space made `rsync --delete` DELETE the destination-only `a.jpg`; only a file literally named `a.jpg` plus a space was kept. The same happened with a trailing tab and with a leading space.
- **rsync source agrees** (rsync's `parse_filter_file`, read at tag v3.5.2, byte-identical at `41bbd895`): a line ends at LF or CR, every other byte is copied into the rule, and a line is skipped only when it is empty or begins with `;` or `#`. Nothing trims.
- **rsync reads more than patterns from such a file:** a line beginning `- ` or `+ ` names its own rule type and a line holding only `!` clears every rule before it (its manual; measured: `+ *.jpg` did not protect `a.jpg`, and `*.jpg` then `!` then `*.png` protected only the `.png`). Blit's pattern files have no such syntax — Q8.
- **Robocopy has no pattern-file option; its file-borne route is a job file** (`/SAVE`, `/JOB`), whose line parsing Microsoft's reference does not describe, so it was measured. Each job was written by robocopy's own `/SAVE` and only the `/XF` value line replaced byte-exact; `/MIR` then ran for real over a destination-only entry beside an unrelated extra file, which was deleted in every case.
  - **The job-file reader strips both ends of a line.** `*.jpg` with a trailing space, with a trailing tab, with four leading spaces, with no indent at all, and with a trailing `::` comment each still protected `a.jpg`.
  - **A line is one name.** `my file.jpg` protected that file and not `my` or `file.jpg`; `*.jpg *.png` on one line protected neither; a quoted `"my file.jpg"` protected nothing (quotes are literal).
  - **Only `::` begins a comment.** Lines `#x.jpg` and `;x.jpg` protected the files of those names.
  - **Robocopy's matcher itself does not trim; the job-file reader does.** On the command line a quoted `/XF "*.jpg "` DELETED `a.jpg`, and a quoted leading space protected only the name that begins with a space.
  - Microsoft's naming rules say a file or directory name must not end with a space or a period (the shell and user interface do not support such names), so on Windows a trailing space in a pattern can never be meant.
- **Blit's own list file already trims:** `FileFilter::load_files_from` (`crates/blit-core/src/fs_enum.rs`) strips both ends of every line and skips blank and `#` lines.
- **A deliberate edge space already has two spellings in blit** (owner question 2026-11-20; measured that day on Linux with blit 1.0.0 built at `863dfcf0`, a local `mirror --yes` over three destination-only names: `a.jpg`, the same with a trailing space, the same after a leading space). The class `[ ]` names the space: `*.jpg[ ]` protected only the trailing-space name and `[ ]*.jpg` only the leading-space name, for exact names as for globs. A space typed inside quotes on the command line is kept as typed: `--exclude '*.jpg '` protected only the trailing-space name. A backslash before the space also worked there; by code read (`backslash_escape(!windows)`) it is not available on Windows, where the backslash separates. Not measured on Windows or macOS.

## Non-goals

- Detecting or depending on the destination's (or source's) case sensitivity. Blit's matching is the same on every machine; the user chooses the mode.
- Transliteration or Unicode normalization (`ß`/`SS`, NFC/NFD `é`): a letter is that letter. The 2026-10-19 APFS reproduction (`*ß` vs `bSS`, `??` vs `s`, `???` vs NFC `É`, each deleted) is EXPECTED behavior under this plan — the exclude did not name those entries — and is re-documented as such, not as a limitation.
- Changing what `?` or a class counts: one byte, as today and as rsync and git (Q10, owner "b" 2026-11-20). Counting characters would be its own plan. What this plan does add is the refusal of a class that cannot match what it shows (AC-10).
- Any per-pattern syntax (regex-style `(?i)`): rejected as requiring knowledge most users do not have.
- Regular expressions (Q7): possible and additive, but a second pattern language with its own rules to settle; they get their own plan. Nothing here guesses a pattern's language from its text.
- A new prompt. `copy` has none and gains none (Q3): an unattended `copy` must not stop at a question. Nothing is asked or printed when `-y` is given.

## Constraints

- **SIMPLE**: two visible options, `--match-case` (default; present so a user can state it — which silences the line, Q9 — and so a saved job records it) and `--ignore-case`; one added prompt line; one sentence of docs each. Owner asked for these (ruling 2026-08-01 permits a visible option when the owner asks).
- **FAST**: `--match-case` changes nothing. `--ignore-case` costs a larger compiled pattern, built once; nothing is done per name beyond the match it already gets; no probe, no extra I/O. No cost at all when the option is absent.
- **RELIABLE / consistent**: one mode per run, carried to the peer at session open so the source walk and the destination's deletion scope read every pattern identically; `--ignore-case` applies to every pattern in the run — `--exclude`, `--include`, and every line of `--exclude-from`/`--include-from` — and never to the literal `--files-from` list (Q2, owner "a" 2026-11-20).
- **Same build only**: the mode is a new wire field; `CONTRACT_VERSION` bumps (8 → 9) and the strict same-build refusal (D-2026-07-05-2) keeps an older peer from reading the field as absent.
- **Letters (Q1, owner "yes" 2026-10-21)**: "ignore case" means **Unicode simple case folding** — one letter to the same letter in another case, across all alphabets, exactly what GNU `grep -i` (UTF-8 locale), ripgrep and Python's regex do. Covers `a`/`A`, `ü`/`Ü`, Cyrillic, Greek `σ`/`Σ`; includes the standard one-to-one oddities `ς`/`σ`, `ſ`/`s`, Kelvin `K`/`k`, `ẞ`/`ß`; NEVER `ß`/`ss` or `ﬁ`/`fi` (one letter to several — "full folding", which no grep, glob or shell does). Windows' own name rule is a frozen subset of this (measured 2026-10-21: `Ü`/`ü` pairs; `ς`/`σ`, `ſ`/`s`, `ẞ`/`ß` do not), so Windows users see a superset of what Windows does — the safe direction. Rejected: the glob library's own case-insensitive mode, which compiles in byte mode and folds `A`–`Z` only (verified in globset 0.4.20 `to_regex_with`: `(?-u)` then `(?i)`); the Amero-centric answer.
- **`?` and classes count bytes (Q10, owner "b")**: `?` matches one byte and a class matches one byte, in both modes, exactly as rsync and git do (measured, Open questions Q10). So `?.txt` does not name `é.txt` — a documented rule, since the names are not known when the command is read. A class holding a non-ASCII character can never match that character, and that IS known when the command is read: it is refused (AC-10).
- **Platform truth**: guards for matching run on every OS (the mode is independent of the disk); the end-to-end mirror guards of `exclude_contract.rs` gain the `--ignore-case` destination-only case and run everywhere, no skips.

- [ ] **AC-9 (`copy` note, Q3)**: `blit copy --exclude '*.cfg' src/ dst/` prints exactly one line of the AC-3 form on stderr before the transfer starts, asks nothing, and copies as today (same exit code, same stdout); the line is bounded as in AC-5 (one line however many patterns, none when no pattern holds a letter) and absent with `--ignore-case`, a typed `--match-case` or `-y` (Q9).

- [ ] **AC-11 (rsync rule lines, Q8)**: a pattern-file line that begins `- ` or `+ `, or holds only `!`, refuses the run before any transfer, prompt or note, naming the file, the line number and the reason (blit's pattern files hold bare patterns, not rsync rules); `[-] name` in a file names a real entry that begins dash-space. ## Design

### Matching

- `crates/blit-core/src/fs_enum.rs`: `FileFilter` gains `ignore_case: bool`. Under `--ignore-case` the PATTERN is widened and names are left exactly as they are (revised 2026-11-20, D-2026-11-20-4, on Codex review change 6): each literal letter of a glob becomes the set of letters that share its Unicode simple case fold (`s` becomes `s`, `S`, `ſ`; `k` becomes `k`, `K` and the Kelvin sign), written as an alternation, and an ASCII class gains its letters' other case; the glob set is then compiled and matched in byte mode against the untouched name, so `?`, `*`, `**` and classes see the same bytes in both modes. The first design folded the name as well, which changed what `?` counted — `ſ` is two bytes and its fold `s` is one, so `??.txt` named `ſ.txt` in one mode and `?.txt` in the other. Nothing is done per name beyond the match. The engine accepts an alternation inside an alternation (run 2026-11-20: `--exclude '{{a,A},{b,B}}.txt'` kept `A.txt` and `b.txt` and deleted `c.txt`), so a pattern's own `{…}` groups widen the same way. NOT globset's `case_insensitive` (ASCII-only). The folding table is the regex engine's own (`regex-syntax`'s simple case folding data, already a dependency through `regex-automata`); no table is written or vendored here. Literal-name and subtree rules (`ExcludeRules`, audit-19) hold no wildcard, so they compare by folded form on both sides. `--include` patterns follow the same bit.
- `crates/blit-core/src/transfers/filter.rs`: `DestinationNames` (the deletion scope) reads pure-glob rules through the same compiled set, so with `--ignore-case` a destination-only `aCache` is in the scope of `*cache`; literal-name lookups through `stored_name` stay as they are (they already use the destination's own pairing for literal names — unchanged by this plan).
- A guard pins the extent of the fold: `Ü`/`ü`, `σ`/`Σ`/`ς`, `ſ`/`s` match; `ß`/`SS` and `ﬁ`/`fi` do not. A second guard pins that `?` counts the same bytes in both modes, on the source walk, in the destination-only deletion scope and in `check`: `ſ.txt` is named by `??.txt` in both modes and by `?.txt` in neither, while `--ignore-case --exclude 's.txt'` names it.

### Class refusal (Q10)

- One check, where globs are already validated: `FileFilter::validate_globs` (`crates/blit-core/src/fs_enum.rs`) and the wire spec's glob validation (`crates/blit-core/src/remote/transfer/operation_spec.rs`), so the CLI, a daemon at session open, a pattern file and a replayed job refuse identically. It walks the pattern bracket-aware (the existing `bracket_class_len`) and refuses any class containing a byte outside ASCII, negated classes and ranges included.
- The escape dialect (`typed_exclude_dialect`) writes an escaped character as a one-character class; it must never produce a non-ASCII class. Today it writes an escaped `é` as a bare `é` (its own test pins this); the slice's guard pins that the check and the dialect cannot disagree.
- No matching changes: an accepted pattern compiles and matches exactly as today.

### CLI and prompt

- `crates/blit-cli/src/cli.rs`: `--match-case` (default, `conflicts_with = "ignore_case"`) and `--ignore-case` on `copy` and `mirror`, the pattern-bearing transfer verbs, and on `check`; one sentence of help each. **Corrected 2026-11-20 while landing slice 1:** the draft also named `move`, but `move` refuses every filter option (R49-F1: its source-delete step would remove what a filter left behind), so it never carries a pattern. It refuses both mode options by name; the matching line is the `mirror` prompt's and the `copy` note's, never `move`'s. A typed `--match-case` is told apart from the default (Q9): it changes no matching and silences the line.
- `check` (Q11) declares its filter options separately in `crates/blit-cli/src/cli.rs` and builds its filter through the same chokepoint (`crates/blit-cli/src/check.rs`): every option a slice adds to the transfer verbs is added to `check` in the same slice, so the two never read a pattern differently.
- `crates/blit-cli/src/transfers/mod.rs` `confirm_destructive_operation` (the existing `mirror` prompt; `move` asks the same question but never carries a pattern, above): when any `--exclude`/`--include` pattern is present AND neither mode option was typed (Q9), add one line built from the first pattern containing a letter: the pattern as typed in quotes, then `matches <as typed> only; capital letters matter (--ignore-case would also match <lower>, <UPPER>)`. `<lower>`/`<UPPER>` are the pattern's literal text with its letters lowered/uppered (wildcards unchanged); whichever equals the typed form is omitted. Further patterns: `and N more patterns`. No line when no pattern holds a letter. With `--ignore-case` or a typed `--match-case` the prompt is the normal delete warning only. `-y` skips the whole prompt as today.
- `copy` (Q3): the same line, from the same builder, printed on stderr with no question beside `warn_unmatchable_excludes` (which already prints a line per unmatchable pattern and goes on), before the transfer starts. Same conditions as the prompt line, minus the prompt.
- No probe of any disk anywhere in this path.

### Pattern files

- `crates/blit-cli/src/cli.rs`: `--exclude-from FILE` and `--include-from FILE` on `copy`, `mirror` and `check` (not `move`, which takes no pattern), repeatable. Read in the CLI (the daemon never sees a file, only the patterns, exactly as with `--exclude` today), appended to the pattern lists before validation, so every downstream path — `FilterSpec` on the wire, `FileFilter`, the deletion scope, the saved job record — sees patterns only and needs no change for the file. One sentence of help each, stating the rule (one pattern per line, `#` starts a comment, `[ ]` writes a space at an edge) and not naming rsync, whose file rule differs (§Prior art, Q8).
- rsync rule lines (Q8): after the shared reader has stripped a line, the PATTERN-file layer refuses one that begins `- ` or `+ ` or is `!` alone. The check sits above the shared reader, not in it, because the `--files-from` list must keep such a name as a name.
- One line reader for both list files (Q5): the line handling inside `FileFilter::load_files_from` — `str::trim`, which strips every Unicode whitespace character at both ends, then skip a blank line or one starting `#` — becomes a helper the pattern files share, so the two cannot drift apart.
- The saved job records the PATTERNS read, not the file path, so a replay does not depend on a file that may have changed (Q6, owner "a" 2026-11-20). This is how a `--files-from` list is already kept — by its lines as read when the job was made (`JobSpec.files_from`, `crates/blit-core/src/job_record.rs`), read once before the transfer starts (`capture_files_from`, review cr-jl5-1) — and how robocopy's saved job keeps its names (inline, measured 2026-11-20). The accepted cost: a pattern added to the file after saving is unknown to a replay, which will not protect what it names, until the job is saved again.

### Wire

- `crates/blit-core/proto/blit.proto` `FilterSpec`: `bool ignore_case` (new field number). `CONTRACT_VERSION` 8 → 9 (`docs/TRANSFER_SESSION.md` frame/contract table, `CHANGELOG.md`). `operation_spec.rs` normalizes it; `NormalizedTransferOperation::from_spec` and the daemon's `validate_spec` carry it into `FileFilter`.

### Records

- `blit_core::job_record` / `JobSpec`: the mode as typed — unstated, `--match-case` or `--ignore-case` — serialized and replayed by `jobs run` and `jobs retry`, so a replay shows or omits the line exactly as the original command did. Three states follow from Q9; the wire still carries the one `ignore_case` bit, since the peer never prints the line.

### Docs

- Release notes: remove the pure-glob limitation bullet; add the rule ("Excludes match exactly as typed. `--ignore-case` ignores capital letters. Before a mirror or move with patterns, blit shows how your pattern will match and asks.") and the two example lines. README and TRANSFER_SESSION likewise. Re-state the 2026-10-19 cases as expected behavior.

### Risks

- A contract bump forces a same-build upgrade of every daemon (already the standing rule, D-2026-07-05-2).
- The widened pattern is larger than the typed one — a few alternatives per letter — and feeds the deletion scope's bounded automaton (O2); the guards of AC-2 pin the fold's extent and the byte count of `?`, and slice 1 measures the automaton's size on a long pattern under `--ignore-case`.
- The prompt line adds one line to a prompt users already see; AC-5 bounds it to one line in every case.
- The `copy` note adds one stderr line to every pattern-bearing `copy` run in the default mode without `-y`; a script that treats any stderr output as failure would notice. Stating `--match-case` quiets it (Q9).
